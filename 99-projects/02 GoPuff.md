# GoPuff — Azure-рішення

## Постановка проблеми
Швидка доставка (година) із сотень мікро-складів. Дві дії: **availability** — «що я отримаю за годину за моєю локацією», і **order** — замовити кілька товарів **без oversell**. Поза межами: оплата, маршрути, пошук, скасування.

Головна ідея, з якої все росте — **різні операції, різна консистентність**:
- **availability** — read-heavy, терпить трохи застаріле → **кеш** (AP);
- **order** — не продати двічі → **атомарна транзакція** (CP).

Ланцюг читання: `координати → зона → які склади дотягнуть → що там у наявності`.

## 1. Гео-фільтр → Azure SQL `geography` + spatial-індекс
- **Що:** вбудований у Azure SQL просторовий тип `geography` + **spatial-індекс** (радіусні запити з коробки, без PostGIS).
- **Чому сюди:** доступність залежить від локації → з координат треба дістати **склади поблизу**, а spatial-індекс робить це швидко навіть на 10k складів.
- **Ключове (контраст):** радіус — це лише **дешевий пре-фільтр** (пряма відстань), **не фінальна відповідь**. «5 км по прямій» ≠ «довезу за годину».

## 2. Час доставки → Azure Maps (Route API)
- **Що:** картографічний сервіс, що рахує **реальний час їзди з пробками**.
- **Чому сюди:** «за годину» — це **час у дорозі**, не пряма відстань (річка без мосту → 40 хв; траса → 12 хв).
- **Ключове (контраст):** дорогий і повільний → кличеш його **лише для кандидатів** із радіус-фільтра (п.1), а не для всіх складів. Патерн **дешевий фільтр → дорога перевірка на жменьці**.

## 3. Кеш → Azure Cache for Redis (два кеші)
- **Що:** два окремі кеші — **гео** (`зона → склади`) і **інвентар** (`inventory:{dcId} → залишки`).
- **Чому сюди:** ~20k запитів/сек на перегляд; кеш знімає навантаження з БД і Azure Maps.
- **Ключове (контраст):** **жоден кеш не ключований по юзеру** — гео **по зоні (geohash)**, інвентар **по складу**. Точна точка юзера унікальна → hit-rate 0; зона спільна для багатьох → hit-rate злітає. Гео **стабільне** (довгий TTL, рідка локальна інвалідація при новому складі), інвентар **мінливий** (короткий TTL).

## 4. Замовлення → Azure SQL, атомарна транзакція
- **Що:** одна **ACID-транзакція на весь кошик** із механізмом no-oversell.
- **Чому сюди:** останній пакет не можна продати двом → потрібна строга консистентність на списанні.
- **Ключове (механіка + контраст):** **SERIALIZABLE** (транзакції ніби по черзі; конфлікт → одна падає) або легший **умовний апдейт** `UPDATE ... SET qty=qty-1 WHERE qty>=1` (0 рядків = вихопили). Будь-яка позиція недоступна → **rollback усього** (колу не забрали) + віддати **конкретну винну позицію**. 🚫 **Не Cosmos** — потрібна **мультипозиційна** ACID-транзакція, а це реляційка.

## Чому availability-кеш може бути застарілим — і це ок
Перегляд показує з кешу (може, трохи старе), але справжній «шлагбаум» — **транзакція замовлення**. Хто спізнився — «вихопили з-під носа». Тому **reads м'які, write строгий** — це не баг, а той самий принцип «різні операції, різна консистентність».

**Суть:** availability — read-heavy → кеш **по зоні** (гео) і **по складу** (інвентар), а «за годину» рахує **Azure Maps** (радіус через `geography` — лише пре-фільтр). Order — **атомарна транзакція в Azure SQL** (SERIALIZABLE/умовний декремент), **rollback усього** + конкретна винна позиція; Cosmos не тягне через мультипозиційність.
