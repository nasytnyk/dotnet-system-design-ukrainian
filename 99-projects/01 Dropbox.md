# Dropbox — Azure-рішення

## Постановка проблеми
Юзер зберігає файли в хмарі й синкає їх між пристроями: **заливає** великі файли, **завантажує**, **шарить по лінку**. Сутності — File, User; API — upload/download.

Нефункціональне, що й визначає рішення:
- **великі файли** (десятки ГБ) з **резюмованим** аплоадом (обрив ≠ качати заново);
- **масштаб** — купа дрібних записів метаданих, **read-heavy** шаринг;
- трафік файлів **не має йти через бекенд**;
- **безпека** — файли приватні, майстер-ключі не світити.

Ключові виклики: (1) де тримати файли, (2) як ефективно залити великий файл, (3) де метадані й шари, (4) авторизація й безпека.

## 1. Файли → Azure Blob Storage (block blobs)
- **Що:** об'єктне сховище; **block blobs** — тип під великі файли (до ~190 TiB, до 50 000 блоків) + access tiers (Hot/Cool/Archive) для здешевлення.
- **Чому сюди:** файли — це великі бінарні об'єкти, не рядки БД; блоб під це й створений. Версіонування й антивірус **нативні** (**Blob versioning** + **Defender for Storage**) — руками не пишемо.
- **Ключове (механіка чанків):** block blob **збирається з блоків** (**Put Block → Put Block List**): обрив → перезаливаєш лише збійний блок (**resume**), блоки йдуть **паралельно**, кожен з перевіркою цілісності. SDK робить це сам (браузер — `@azure/storage-blob`, десктоп — `BlobClient.UploadAsync`).

## 2. Прямий аплоад → SAS
- **Що:** **SAS (Shared Access Signature)** — короткоживучий URL із вшитим дозволом рівно на цей блоб.
- **Чому сюди:** трафік великих файлів **не має йти через бекенд** (він став би бутилочним горлом). SAS дає клієнту лити **напряму в Blob Storage**, минаючи апку.
- **Ключове (контраст):** бекенд лише **підписує перепустку** (який блоб, права, доки діє), а Blob Storage перевіряє підпис — трафік іде **повз бекенд**. **User Delegation SAS** підписує не майстер-ключем стораджу, а **Entra ID** → головний ключ не світиться, і токен можна відкликати.

## 3. Великі файли → десктоп-агент (не браузер)
- **Що:** нативний sync-агент на .NET замість браузера для файлів на десятки ГБ.
- **Чому сюди:** браузер має **ліміти пам'яті** й крихкий на таких обсягах; агент тримає resume/паралельність стабільно.
- **Ключове:** агент на .NET **кросплатформний** — одна кодова база під Win/Mac/Linux, а `FileSystemWatcher` під капотом лягає на inotify/FSEvents.

## 4. Метадані і шари → Cosmos DB
- **Що:** метадані файлів (`fileId → інфа`) і шар-лінки (`shareId → ціль`) у Cosmos.
- **Чому сюди:** доступ — **lookup по ключу**, гнучка схема, горизонтальний масштаб під купу дрібних записів, read-heavy (публічний лінк смикають анонімно).
- **Ключове (механіка TTL):** у Cosmos **нативний TTL** — протерміновані шар-лінки **зникають самі**, без жодної cron-джоби (порівняй: у SQL довелося б крутити прибиральну задачу).

## 5. Авторизація → Entra ID / JWT
ASP.NET Core JWT Bearer middleware сам валідує токен (підпис/issuer/expiry), видає **Microsoft Entra ID** — свого коду нуль, лише конфіг + `[Authorize]`.

## 6. Безпека → з коробки
- **In transit:** TLS + SAS тільки по HTTPS;
- **At rest:** Azure Storage шифрує **за замовчуванням** (AES-256);
- **Доступ:** короткоживучі SAS + **Private Endpoints**, щоб блоб не стирчав у публічний інтернет.

## Свідомо не тягнемо
CDN, компресію, real-time синк (аж до SignalR) — для цього рівня стрільба з гармати по горобцях.
