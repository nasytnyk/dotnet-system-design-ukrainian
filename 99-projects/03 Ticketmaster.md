# Ticketmaster — Azure-рішення

## Постановка проблеми
Продаж квитків на події (концерти/спорт): юзер **шукає** подію, дивиться **вільні місця**, **бронює**. Головняк: на гарячу подію налітають **мільйони одночасно** (Тейлор Свіфт), і не можна продати **одне місце двом**.

Ядро (read-heavy перегляд/пошук + строга транзакція на бронь) — як у подібних кейсах. Нове й цікаве — п'ять речей нижче.

## 1. Hold місця → Redis з TTL
- **Що:** тимчасова бронь місця в Redis: `SET seat:{id}=userId NX EX 600`.
- **Чому сюди:** місце треба **притримати за юзером на 5–10 хв, поки платить**, і **само звільнити**, якщо не встиг. Redis швидкий і має вбудований TTL.
- **Ключове (контраст):** **`NX`** = distributed lock (взяв, лише якщо вільно), **`EX`** = авто-звільнення **без cron**. Hold живе **тільки в Redis**; база чіпається **лише на оплаті** (durable «booked»). Порівняй: hold у базі вимагав би cron-прибирання протермінованих + зайвий запис на кожен клік.

## 2. Ажіотаж (10M на подію) → кеш шарами
- **Що:** багатошаровий кеш метаданих події.
- **Чому сюди:** мільйони читають **ту саму** подію → воно шалено кешоване.
- **Ключове:** читання осідають **шарами** — **CDN** (метадані) → **Redis** (кластер + репліки) → апка за балансувальником. До бекенду доходить усе менше.

## 3. Черга очікування → буфер перед бронюванням (найцікавіше)
- **Що:** віртуальна кімната очікування, що **дозовано впускає** юзерів у бронювання.
- **Чому сюди:** бронювання витримує N активних, а прийшло 10M → впустити всіх = смерть. Черга **перетворює сплеск на рівний потік**.
- **Ключове (механіка токена):** прийшов → дістав **позицію + токен** (кукі/підписаний рядок) = **місце в черзі** (закрив вкладку → токен береже позицію); черга в **Redis** (list/ZSET, FIFO); **клапан** впускає дозовано (N/сек або «один вийшов — одного впустили»); впустили → видали **admission-токен** (підписаний, час-обмежений) → **лише з ним** пройдеш у бронювання. Вхід дешевий (Redis + **статична сторінка на CDN**), тож 10M не валять саму чергу.
- Azure: Redis (черга), SignalR/SSE (позиція), Front Door/APIM (ворота, rate limit).

## 4. Пошук → Azure AI Search
- **Що:** керований повнотекстовий пошук (аналог Elasticsearch).
- **Чому сюди:** шукати подію за словом/датою треба з **толерантністю до одруків**, а не точним збігом.
- **Ключове (контраст):** **інвертований індекс + fuzzy** замість SQL `LIKE` (той повільний і без одруків); синхрон із БД через **CDC/indexer**; масштаб — **репліки + партиції**. Не піднімаєш власний Elastic.

## 5. Жива мапа місць → SSE
- **Що:** SSE пушить оновлення статусу місць у реальному часі.
- **Чому сюди:** місця гаснуть наживо → клієнту треба бачити зміни без F5. SSE — однонапрямний стрім, простий.
- **Ключове (контраст):** стережись **буферизації / idle-таймаутів на краю** (вимкнути буфер, keep-alive), або бери **Azure SignalR** для масштабу. Для мега-подій живу мапу дають **лише впущеним** (черга з п.3 гейтить фан-аут) — не пушиш мільйонам.

**Суть:** нове в Ticketmaster — **hold через Redis-TTL** (`NX`-лок + авто-звільнення, база лише на оплаті), **черга очікування** (токен = місце в черзі, admission-токен = дозвіл увійти), **Azure AI Search** замість `LIKE`, **SSE/SignalR** для живої мапи, а читання ловиться кешем **шарами** (CDN→Redis→апка).
