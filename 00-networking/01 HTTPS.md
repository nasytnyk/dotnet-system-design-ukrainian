# HTTPS у .NET на Azure

## На Azure TLS термінує НЕ твоя апка, а край
App Service усередині — це два шари:
- **Front ends** — спільний (мультитенантний) пул **реверс-проксі** (reverse proxy = посередник, що стоїть *перед* серверами й розкидає їм запити). Тут живуть сертифікати, **тут термінується TLS** (тобто розшифровується), тут балансування й маршрутизація за іменем хоста. «Пул» — бо це цілий флот однакових stateless-машин, будь-яка обробить будь-який запит.
- **Workers** — інстанси, де крутиться **твоя апка** (Kestrel + код).

## Порядок зв'язку (крок за кроком)
1. DNS резолвить `твояапка.azurewebsites.net` → **спільна IP front-end пулу**.
2. HTTPS-запит з інтернету лягає на **якийсь front end** із пулу.
3. Front end **термінує TLS** (розшифровує), дивиться `Host` → розуміє, що це твоя апка, і пересилає **вже відкритий HTTP** по внутрішній мережі на **один із воркерів**.
4. Kestrel отримує **звичайний HTTP** + дописані заголовки: `X-Forwarded-Proto: https`, `X-Forwarded-For: <справжній IP клієнта>`, `X-Forwarded-Host`.
5. Відповідь іде назад через front end, який **пере-шифровує** її клієнту.

Аналогія: **ресепшн бізнес-центру**, спільний для багатьох компаній. Гість заходить захищеним каналом, ресепшн перевіряє серт, розшифровує, дивиться, до кого гість (`Host`), і веде на потрібний поверх (воркер). Твоя апка говорить **тільки з ресепшеном, ніколи з вулицею напряму**.

## Пастка деплою
Апка сидить **за проксі** і TLS **взагалі не бачить** — до неї дійшов уже розшифрований запит. Хто цього не знає, отримує:
- `Request.Scheme == "http"` → `UseHttpsRedirection` може піти в **нескінченний редірект-цикл**;
- згенеровані посилання виходять `http://` → **ламаються OAuth redirect URI** й лінки;
- `RemoteIpAddress` — це **внутрішній IP front end'а**, а не клієнта → логи й rate-limit по IP брешуть.

## Kestrel на Azure — як зробити грамотно
Головне правило: **не намагайся термінувати TLS у самому Kestrel, коли це вже робить край.** Грамотний дефолт:
- Kestrel слухає **звичайний HTTP**, а TLS лишаєш платформі (front end App Service / ingress Container Apps);
- вмикаєш middleware **`ForwardedHeaders`** (`app.UseForwardedHeaders()`), щоб апка читала `X-Forwarded-Proto`/`-For` і розуміла, що оригінал був HTTPS і хто справжній клієнт. Оце і є та відповідь, що відрізняє того, хто деплоїв, від того, хто ні.

Термінувати TLS **у самому Kestrel** треба лише коли хочеш **end-to-end шифрування** (пере-шифрувати навіть край→воркер) — тоді Kestrel вантажить серт і термінує сам. За замовчуванням це не потрібно.

## Звідки серт узагалі береться
Серт **не «народжується» в Key Vault** — Key Vault це сейф. Пару ключів може згенерувати Key Vault (або ти), але **підписує серт завжди CA** (центр сертифікації, зовнішній) — тільки він дає довіру, якій вірить браузер. Для внутрішнього mTLS вистачить self-signed (довіру роздаєш собі сам). **А найсолодше для App Service — App Service Managed Certificate: Azure сам іде до CA, бере безкоштовний серт для твого домену й автоматично його поновлює — ти не торкаєшся ні CSR, ні CA, ні ротації.** Оце азурівська перевага: HTTPS без єдиного ручного руху навколо сертів.

## Найпростіший спосіб прикрутити HTTPS (App Service)
Якщо серт **свій** (не Managed Certificate) — найпростіше **імпортувати його з Key Vault прямо в TLS-налаштування App Service**: платформа сама тягне серт і термінує TLS на front end, а ти **в Kestrel не вантажиш нічого**. Що для цього треба:
- серт лежить у **Azure Key Vault** (централізоване сховище з авторотацією);
- у твоєї апки є доступ до цього Key Vault.

## Звідки серт і хто його стереже: Key Vault + Managed Identity
Серт (разом із приватним ключем) лежить у **Key Vault**, а апка тягне його **не паролем**, а через **Managed Identity** — це «автообліковка» від Azure, **якій Key Vault довіряє**: жодного секрету в коді. Потік: Managed Identity → бере токен у Entra ID саме для Key Vault → Key Vault перевіряє права (RBAC) → віддає серт. Оце й розриває замкнене коло «щоб дістати пароль зі сховища паролів, треба пароль».

## А всередині мережі? (zero trust + комплаєнс)
Після краю трафік до воркерів часто йде **звичайним HTTP по приватній мережі** — і для багатьох це норм. Але:
- **zero trust** («не довіряй нікому, вважай, що мережу вже зламали») каже шифрувати **навіть всередині** — щоб зловмисник, який уже проник, не читав трафік і не вдавав сервіс;
- **комплаєнс** (PCI/HIPAA) це часто прямо **вимагає**.

Робиться прозоро через **mesh/Dapr mTLS** (взаємний TLS, де обидві сторони показують серт) — без коду в апці. Понтова згадка, від якої відгонить маркетингом, але на співбесіді звучить дорого.

## Де це оверкіл
- **Термінувати TLS у самому Kestrel на App Service**, коли край уже це робить — подвійна робота + зайва морока з сертами.
- **Пере-шифровувати край→воркер у замкненій VNet** без комплаєнс-вимоги — палиш CPU й серти заради маргінального виграшу.
- **Крутити власне поновлення Let's Encrypt** у застосунку, коли платформа дає керовані серти безкоштовно. *(Let's Encrypt — безкоштовний неприбутковий центр сертифікації (CA), що видає TLS-серти автоматично через протокол ACME; серти короткоживучі (90 днів) і поновлюються самі.)*

*Перевага Azure тут — єдиний **Key Vault** з авторотацією сертів через увесь стек (App Service / Container Apps / Front Door).*
