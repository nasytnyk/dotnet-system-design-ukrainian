# SSE: стрімінг LLM і пастка буферизації на краю Azure

**Server-Sent Events (SSE)** — **односторонній** потік сервер→клієнт по одному довгоживучому HTTP-з'єднанні (`text/event-stream`). У браузері нативний `EventSource` із **вбудованим авто-реконектом** і `Last-Event-ID` (відновлення з місця обриву). Клієнт→сервер при цьому йде звичайними HTTP-запитами.

## Головний сучасний кейс: стрімінг токенів LLM
Коли відповідь AI «друкується» по словах — це **SSE**. Так стрімлять токени API OpenAI/Anthropic, і так само **Azure OpenAI Service**: викликаєш зі стрімінгом — відповідь **приходить як SSE**. Тобто AI-апка на Azure, що друкує відповідь наживо, — це SSE наскрізь.

Інші кейси: живі стрічки/нотифікації, прогрес довгих задач, live-tail логів — усе, де клієнт лише **отримує**.

## У .NET
- **.NET 9** — клієнтський парсер `System.Net.ServerSentEvents.SseParser<T>` (щоб **споживати** SSE, напр. від LLM);
- **.NET 10** — серверний `TypedResults.ServerSentEvents(...)` поверх `IAsyncEnumerable<SseItem<T>>` (нативний SSE з minimal API).

## Головна пастка: буферизація й таймаути на краю Azure
SSE тримає **довге відкрите з'єднання** — і саме це ламають краєві компоненти:
- **Idle timeout** на **Front Door / Application Gateway** рве тиху сесію → **фікс:** періодичний keep-alive (`: ping\n\n`) або вищий таймаут;
- **буферизація відповіді** — проксі накопичує замість негайного флашу, події не доходять наживо → **фікс:** вимкнути буферизацію;
- **APIM** за замовчуванням буферить → для стрімінгу (зокрема **APIM перед Azure OpenAI**) треба ввімкнути **passthrough стріму**, інакше «друкування» прилетить одним шматком у кінці.

Знати «SSE ламається об буферизацію/таймаути краю → keep-alive + no-buffering» — це продакшн-сигнал, що ти це деплоїв.

## Межа / де НЕ треба
- Потрібен **дуплекс** (клієнт теж часто шле) → WebSocket.
- **Бінарні дані** → SSE тільки текст (base64-оверхед) → WebSocket.
- **Рідкі оновлення** → тримати з'єднання марно, дешевше polling.
- **HTTP/1.1 ліміт ~6 з'єднань на домен** — багато паралельних SSE вичерпують його; знімає **HTTP/2 мультиплекс**.

**Суть:** SSE — простий односторонній стрім сервер→клієнт по HTTP з нативним авто-реконектом; головний сучасний кейс — **стрімінг токенів LLM (Azure OpenAI)**, а головна азурівська пастка — **буферизація й idle-таймаути на Front Door/APIM**, які фіксяться keep-alive і вимкненою буферизацією.
