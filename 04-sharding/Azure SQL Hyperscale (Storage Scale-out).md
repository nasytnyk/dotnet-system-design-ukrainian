# Azure SQL Hyperscale — «шардинг» storage

## Головне застереження
Hyperscale — це **не класичний шардинг** твоїх таблиць по вузлах. Це **одна логічна БД**, у якій **автоматично розподіляється сховище**. Тобто масштаб є, але через інший механізм — тому воно в цьому списку радше «для контрасту».

## Як улаштований (дезагрегація)
Класична БД тримає компʼют і диск разом. Hyperscale їх **розчіплює** на шари:
- **compute** (основна нода + read-репліки);
- **page servers** — тримають дані **шматками (по ~128 ГБ)**, і саме тут «шардинг»: сховище **авто-розподіляється** по багатьох page servers, масштабуючись **до 100 ТБ**;
- окремий **log service** і кеш на локальних SSD.

Тобто «розподіляється» **сховище**, а не навантаження запитів по шардах.

## Виграш
- Масштаб **до 100 ТБ** без ручного шардингу;
- **швидкі snapshot-бекапи й відновлення** (миттєві, бо на рівні сховища);
- **read-репліки** масштабують читання;
- швидкий scale up/down компʼюту (він відв'язаний від диска).

## Межа (головне)
- Це **одна БД** — запис іде через **одну primary-ноду** (не масштабуєш запис шардингом);
- **не заміняє справжній шардинг**, коли треба розкидати **навантаження запису** по вузлах — тоді це Citus/Cosmos;
- overkill для дрібної БД.

**Суть (пара речень для співбесіди):** Hyperscale — це **не шардинг таблиць**, а **дезагрегація сховища**: компʼют відв'язаний від диска, а дані авто-розподілені по **page servers** до 100 ТБ, з миттєвими бекапами й read-репліками. Дає масштаб **однієї логічної БД** без ручного шардингу; але **запис усе одно через одну ноду**, тож для розподілу навантаження запису це Citus/Cosmos, а не Hyperscale.
