# Автентифікація / авторизація API в Azure (без механіки)

## Два слова
- **AuthN (автентифікація)** — *хто ти* (доводиш особу);
- **AuthZ (авторизація)** — *що тобі можна* (права).

## Головна ідея: логін ти не пишеш — його робить Entra
- **Microsoft Entra ID** — постачальник ідентичності: тримає юзерів/сервіси і **видає токени**. Свою систему паролів ти не будуєш.
- **JWT** — підписаний «паспорт», який клієнт носить із собою; твоє API його **саме перевіряє** (а не питає Entra щоразу).

## Що з чим зʼєднується (загалом)
1. Юзер логіниться через **Entra** → отримує **токен**;
2. клієнт шле цей токен **з кожним запитом** до API;
3. API **перевіряє токен** → пускає або відмовляє (**403**);
4. що саме дозволено — вирішують **права в токені**.

*(Технічний танець між кроками 1–2 — окрема тема; тут головне — хто кому що дає.)*

## Хто кличе
- **Юзери** — люди логіняться;
- **Сервіси (machine-to-machine)** — тут зірка **Managed Identity**: Azure дає твоєму сервісу ідентичність, і він ходить до Key Vault / SQL / Storage **без паролів у коді**.

## Де це вмикається в Azure (адаптери)
- **Твоє API** — валідує токен (кілька рядків конфігу + `[Authorize]`, логіку з нуля не пишеш);
- **APIM** — може перевіряти токен **на краю**, ще до API;
- **App Service / Container Apps «Easy Auth»** — платформа робить логін **сама, без коду**;
- **Azure RBAC** — окремо: хто може **керувати Azure-ресурсами**.

## Одне важливе розрізнення
- **Авторизація в апці** — що юзер може робити всередині твого API;
- **Azure RBAC** — хто може чіпати самі Azure-ресурси (роль на Key Vault тощо).

Обидва через Entra, але про різне.

**Суть:** не будуй auth сам — **делегуй Entra** (вона видає токени), а **API / APIM їх перевіряють**; Azure→Azure ходить **passwordless через Managed Identity**. Права бувають двох рівнів: усередині апки (що юзеру можна) і Azure RBAC (хто керує ресурсами).
