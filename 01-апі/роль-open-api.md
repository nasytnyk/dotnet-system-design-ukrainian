## Життєвий шлях OpenAPI-документа

**1. Народження — .NET його генерує.**
Ти пишеш ендпоінти (minimal API з `TypedResults`/`WithName` або контролери з `[ProducesResponseType]`). Фреймворк **читає їхні метадані** й будує з них єдиний документ — опис усіх маршрутів, параметрів, схем запиту/відповіді й авторизації. З .NET 9 це роблять вбудовані `AddOpenApi()` + `MapOpenApi()`, які віддають документ за адресою типу `/openapi/v1.json`. Це **code-first** підхід: код — джерело, спека — похідне.

**2. Куди він іде далі — споживачі.**
Народжений документ сам нічого не робить; його цінність у тому, **хто його читає**:
- **UI-рендерери** (Swagger UI / Scalar / Redoc) — перетворюють JSON на живу інтерактивну документацію для людей;
- **генератори клієнтів** (Kiota / NSwag) — з того самого файлу роблять типізовані SDK під C#/TS/інше, щоб фронт і сусідні сервіси не писали клієнт руками;
- **тести й моки** — контрактні тести, мок-сервери, імпорт у Postman.

**3. Що з ним відбувається — стає єдиним джерелом правди.**
Ключова ідея: API описаний **один раз**, і все решта — доки, клієнти, конфіг шлюзу, моки — **виводиться з цього одного контракту**. Опис не розповзається по коду й вікі. У CI/CD документ **експортується на кожен білд** і автоматично публікується далі — саме тут вступає Azure.

**4. До чого тут Azure — контракт їде в хмару.**
- **Azure API Management** імпортує цей OpenAPI → сам будує операції шлюзу, скелет політик і документацію в developer portal. Тобто твоя спека стає **конфігом шлюзу**.
- **Azure API Center** складає всі такі документи в **централізований каталог API** компанії — інвентаризація, пошук, governance.
- **Azure Functions** мають OpenAPI-розширення, щоб serverless-ендпоінти теж віддавали спеку в цей самий конвеєр.

**Мораль:** .NET генерує контракт із коду → контракт годує людей (доки), машини (клієнти) і шлюз (APIM/API Center) → API описаний раз, а живе скрізь.
