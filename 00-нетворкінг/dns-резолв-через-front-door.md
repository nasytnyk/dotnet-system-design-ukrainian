# Шлях запиту до Azure-апки: від домену до відповіді

**Azure Front Door** — це глобальний L7 (рівня застосунку) реверс-проксі й єдина точка входу перед твоєю апкою: розподілений по світу edge, що термінує TLS, кешує, захищає (WAF) і маршрутизує запит на найкращий живий бекенд. Трафік реально тече крізь нього.

## Що налаштовано
- Домен `dzhigurda.com` можна купити **прямо в Azure — Azure App Service Domains** (сам створює DNS-зону й усе зшиває).
- У зоні `dzhigurda.com` — **alias record**, що вказує на **Front Door** (alias сам оновлюється й лягає навіть на голий apex-домен).
- **Front Door спереду, за ним — наша апка** (напр. App Service у якомусь регіоні) як **origin** (джерело).

## Що відбувається, коли хтось увів адресу
1. **Браузер/ОС перевіряє свій DNS-кеш.** Є і TTL живий → резолв пропускається. Припустимо, перший візит.
2. ОС питає **recursive resolver** (сервер провайдера або `8.8.8.8`) — він бігає замість тебе.
3. Резолвер іде по ієрархії: **root → TLD `.com` → Azure DNS** (authoritative для домену, бо туди делеговано).
4. **Azure DNS повертає anycast-IP Front Door — один IP на весь світ.**
5. Резолвер **кешує** відповідь (на TTL) і віддає IP браузеру.
6. Браузер конектиться: **TCP + TLS**. Anycast приземляє з'єднання на **найближчий edge Front Door** (та сама IP, але фізично різні точки для Києва й Токіо).
7. **Front Door обробляє:** термінує TLS, дивиться Host/шлях, застосовує WAF і кеш; якщо треба — обирає **живий origin** і пересилає по своєму приватному бекбоні.
8. **Апка відповідає** → назад через Front Door (може закешувати) → браузер. Готово.
9. **Наступні запити** — без повного резолву (DNS у кеші), по перевикористаному з'єднанні.

## Що тут головне
- **Anycast:** один IP, але трафік завжди йде на найближчий edge.
- **Front Door стоїть у потоці трафіку** — сам термінує TLS, кешує й обирає живий origin (тому й перемикання на здоровий бекенд миттєве).
