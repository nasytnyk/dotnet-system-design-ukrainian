# GoPuff — .NET/Azure

## Задача (бізнес)
Швидка доставка (година) з сотень мікро-складів. Дві речі: **availability** — «що я отримаю за годину за моєю локацією», і **order** — замовити кілька товарів **без oversell**. Поза межами: оплата, маршрути кур'єрів, пошук, скасування.

## Головна ідея: різні операції — різна консистентність
- **availability** — read-heavy, терпить трохи застаріле → **кеш**;
- **order** — строга консистентність, не продати двічі → **атомарна транзакція**.

## Availability (шлях читання)
Ланцюг: `координати → округлити в зону → які склади дотягнуть → що там у наявності`.
- **Front Door → APIM (валідація JWT) → App Service (ASP.NET Core)**;
- **гео-шар** (зона → склади в досяжності):
  - «склади в радіусі» — spatial-запит в **Azure SQL** (тип **`geography`** + **spatial-індекс**), а не пряма відстань руками;
  - радіус — лише **дешевий фільтр**; реальний «за годину» рахує **Azure Maps (Route API)** з пробками — і **лише для кандидатів**;
  - кешуй **по ЗОНІ (geohash/grid), не по унікальній точці юзера** → багато юзерів на один ключ; TTL довгий (гео стабільне), інвалідація **рідка й локальна** (новий склад → перерахувати сусідні зони);
- **інвентар-шар:** кеш ключований **по складу** (`inventory:{dcId}`), **короткий TTL** (мінливе);
- обидва кеші — **Azure Cache for Redis**.

> Ключове: **жоден кеш не ключований по юзеру** — гео по зоні, інвентар по складу. Саме тому кеш узагалі працює.

## Order (шлях запису)
- **одна атомарна транзакція** на **весь кошик** в **Azure SQL**;
- механізм no-oversell:
  - **SERIALIZABLE** — транзакції виконуються ніби по черзі; конфлікт на останньому товарі → одна падає з serialization-помилкою;
  - або легший **умовний апдейт**: `UPDATE ... SET qty = qty-1 WHERE qty >= 1` (0 рядків = вихопили);
- будь-яка позиція недоступна → **rollback усього** (колу не забрали) → віддати **конкретну винну позицію** → юзер коригує й ретраїть.
- Це **CP-вибір**: краще відмовити, ніж oversell.

## Чому availability-кеш може бути застарілим — і це ок
Перегляд показує з кешу (може, трохи старе), але справжній «шлагбаум» — **транзакція замовлення**. Хто спізнився — «вихопили з-під носа». Тому **reads м'які, а write строгий**.

## Azure-карта (з обґрунтуванням)
- **вхід:** Front Door (+ CDN для статики), **APIM** (JWT, rate limit);
- **апка:** App Service / Container Apps (ASP.NET Core minimal API);
- **гео:** Azure SQL `geography` + spatial index (радіус) → **Azure Maps** (час їзди);
- **кеш:** Azure Cache for Redis (гео-зони + інвентар);
- **істина + замовлення:** Azure SQL (атомарна транзакція, SERIALIZABLE/умовний апдейт);
- 🚫 **Cosmos свідомо НЕ беремо** — потрібна мультипозиційна ACID-транзакція, а це реляційка.

**Суть (для співбесіди):** availability — read-heavy → кеш **по зоні** (geohash) для гео і **по складу** для інвентаря, а «за годину» рахує **Azure Maps** (радіус лише пре-фільтр через `geography`/spatial-індекс). Order — **одна атомарна транзакція в Azure SQL** (**SERIALIZABLE** або умовний декремент), **rollback усього** при нестачі + конкретна винна позиція. Reads м'які (кеш терпить старе), write строгий (не oversell) — **різні операції, різна консистентність**. Cosmos тут не тягне через мультипозиційну транзакцію.
