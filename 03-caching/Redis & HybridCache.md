# Redis & HybridCache

## Кеш на Azure = Redis
Керованого Memcached на Azure нема → кеш це **Azure Cache for Redis** (керований Redis). Тіри Basic/Standard/**Premium** (кластеризація, persistence, гео-реплікація, zone-redundancy); є новіший **Azure Managed Redis** (на Redis Enterprise: модулі RediSearch/RedisJSON, active geo-replication).

## HybridCache (.NET 9) — головне
Новий уніфікований кеш, що об'єднує **два рівні**:
- **L1 — локальна пам'ять апки:** без мережі, наносекунди, але **per-instance** і гине при рестарті;
- **L2 — Redis:** мілісекунди (мережевий стрибок), зате **спільний для всіх інстансів** і переживає рестарт.

Аналогія: **L1 — шухляда твого столу** (миттєво, мала, лише твоя); **L2 — спільна комора офісу** (треба пройтись, зате велика й для всіх).

HybridCache — **диригент над ними**. За `GetOrCreateAsync(key, factory)`:
1. дивиться **L1** → є → віддав миттєво;
2. міс → дивиться **L2 (Redis)** → є → віддав **і поклав у L1** (наступного разу миттєво);
3. міс → викликає **factory** (рахує з БД) → кладе в **обидва**.

Тобто реєструєш **Redis як L2**, а HybridCache надбудовує локальний L1 + серіалізацію + інвалідацію за тегами. Без Redis працює теж — але тоді лише **L1, per-instance**.

## Stampede protection
Ключ протух, і **сотні запитів одночасно** летять за ним → без захисту всі кинулись би рахувати factory й задовбали базу (**thundering herd**). HybridCache **склеює конкурентні виклики**: factory виконується **один раз**, решта чекають його результат.

## Патерн / межа
- **Cache-aside** — дефолт: дивишся кеш → міс → тягнеш із БД → кладеш у кеш.
- **Інвалідація** — найважче: TTL + теги.
- **Тільки L1** (без Redis) — per-instance, не для кількох інстансів.

**Суть:** на Azure кеш = **Redis** (Memcached нема). У .NET 9 зірка — **HybridCache**: об'єднує **L1 (локальна пам'ять) + L2 (Redis)** в одному API, сам заповнює обидва рівні й дає **stampede protection** (склеює одночасні міси в один виклик). Redis у ньому — це L2.
