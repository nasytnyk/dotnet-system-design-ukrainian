# HTTP/3: виграш і як з ним працює Azure

## У чому виграш
Семантика HTTP та сама — змінюється **транспорт**: стек тепер **HTTP/3 → QUIC → UDP** (замість HTTP/2 → TCP). QUIC бере голий UDP і реалізовує транспорт заново, звідси три виграші:

- **Немає head-of-line blocking.** У HTTP/2 на TCP один загублений пакет стопить **усі** мультиплексовані стріми (TCP віддає байти строго по порядку). QUIC веде надійність **пока́жно (per-stream)** — втрата в стрімі A не блокує B і C.
- **Швидший старт з'єднання.** TLS 1.3 **вшитий** у QUIC → хендшейк за **1-RTT** (0-RTT для повторного) замість TCP+TLS у 2–3 обміни.
- **Connection migration.** З'єднання йде по `connection ID`, а не `IP:порт`, тому переживає зміну мережі (wifi→мобільний) **без реконекту**.

## Які сценарії виграють
- **мобільні на стільниковому / поганому wifi** — втрати пакетів + перемикання мережі (найбільший виграш);
- **юзери далеко від сервера / високий пінг** — економія RTT на хендшейку;
- **сторінка з купою паралельних ресурсів** по lossy-каналу — мультиплекс без HOL;
- **юзери, що міняють мережу посеред сесії** — комʼютери, мобільні застосунки.

## Де виграшу нема (чесна межа)
На **чистій швидкій мережі різниця майже нульова** (HOL кусає лише при втратах), а QUIC ще й жаркіший по CPU. Для сервіс-до-сервіса всередині ДЦ — не треба (там HTTP/2/gRPC). Це **edge/клієнт-оптимізація для реальних юзерів**, а не архітектурний важіль.

## Фронтенд про це не знає
HTTP/3 **прозорий для фронтенд-коду**: `fetch()`, `<img>` тощо однакові на будь-якому HTTP — протокол обирає мережевий стек браузера, це рівень **нижче** застосунку. Побачити можна в DevTools (колонка **Protocol** → `h3`), але форснути з коду не можна. Фронт **виграє без жодних змін**.

## Як вмикається — повністю автоматично
Клієнт і сервер домовляються самі, без ручних дій:

1. **Перше з'єднання завжди по TCP** (HTTP/1.1/2).
2. Сервер додає заголовок **`Alt-Svc: h3=":443"`** — «я ще й HTTP/3 на цьому порту». Це **момент виявлення**.
3. Браузер запам'ятовує і на **наступному** з'єднанні пробує підняти **QUIC/UDP**. Успіх = **перемикання** на HTTP/3.
4. Якщо UDP заблоковано (корпоративний фаєрвол) — тихо **лишається TCP**.

Тобто перемикання **автоматичне, кероване клієнтом, per-origin і кешоване**; **перше з'єднання практично ніколи не HTTP/3** (спершу TCP його рекламує). Новіший **DNS-запис HTTPS/SVCB** дозволяє пробувати QUIC уже на **першому** з'єднанні, минаючи TCP-розгін.

## Як Azure з ним працює
- **Azure Front Door підтримує HTTP/3** — вмикаєш галочкою, і **край говорить HTTP/3 з клієнтами** (сам додає `Alt-Svc`), а до origin ходить звичним HTTP/2. Клієнтський виграш отримуєш **не чіпаючи апку**.
- **Kestrel** уміє HTTP/3 з **.NET 7** (через `libmsquic`), але руками вмикати сенсу мало, коли є Front Door.

## Фінтех і суворий нагляд — обережно
HTTP/3 **продвинутіший і оптимізованіший**, але QUIC іде по UDP у користувацькому просторі й **гірше піддається інспекції** (DPI/IDS/WAF будувалися під TCP+TLS). Тому там, де потрібен **точний трекінг і аудит трафіку** (фінтех тощо), його часто уникають або зовсім блокують UDP/443. Висновок: HTTP/3 — краще для **«контентних» цілей** (медіа, споживчий веб, де головне швидкість), а не для суворо-наглядових. Якщо все ж у фінтеху — тільки на **споживчому краю через Front Door**, ніколи всередину чи партнерам.
