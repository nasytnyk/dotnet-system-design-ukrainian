# GraphQL на Azure: спокуса й граблі

**GraphQL** — клієнт **одним запитом замовляє точно потрібні поля** з типізованого графа через єдиний `/graphql` (на відміну від REST, де форму диктує сервер).

**Як Azure це дає:**
- **Azure Data API Builder (DAB)** — опенсорс-рушій, що **авто-генерує GraphQL (і REST) над базою** (Azure SQL, Cosmos, Postgres, MySQL) з конфігу, **без коду**; крутиться контейнером або в Static Web Apps.
- **Hot Chocolate** — головна .NET-бібліотека для **кастомного** GraphQL-сервера.
- **APIM** — GraphQL-підтримка спереду (валідація й ліміти).

## Спокуса
DAB дає **GraphQL над своєю базою за хвилини, нуль коду** — лише конфіг (сутності, зв'язки, ролі). Для прототипів, внутрішніх тулів і data-API це реально магія: жодних резолверів чи бойлерплейту.

## Граблі (яких у REST не було)
- **Кеш ламається** — усе POST на один `/graphql`, кеш по URL безсилий → втрачаєш безкоштовний CDN/HTTP-кеш. *(фікс: persisted queries)*
- **DoS складністю** — клієнт сам пише запит, тож глибокий/широкий вибухає навантаженням на базу. *(фікс: ліміти глибини й складності)*
- **Втрачений per-endpoint контроль** — усе один POST, і шлюз/WAF не бачить, що саме питають → rate-limit і роутинг за шляхом не працюють.
- **Авторизація по полях**, а не на ендпоінт — один запит чіпає багато сутностей, легко перевідкрити зайве.
- **«Авто» = без запобіжників** — DAB за замовчуванням не змушує це харденити й може оголити структуру БД.

## Коли брати, а коли обпечешся
- **Брати:** внутрішні тули, прототипи, довірені клієнти, гнучкі read-API — мережа своя, навантаження кероване, граблі не стріляють.
- **Обпечешся:** публічний інтернет, масштаб, фінтех — там або **серйозно хардениш** (ліміти глибини/складності, persisted queries, **APIM спереду**), або лишаєшся на REST.

**Суть:** Azure Data API Builder робить GraphQL майже безкоштовним, але рахунок приходить пізніше — зламаний кеш, DoS-поверхня, втрачений per-endpoint контроль. Для внутрішнього — бери й радій; для публічного — спершу хардениш або лишаєшся на REST.
