# Azure SQL Database — шардинг (DIY, Elastic tools)

## Головне: тут шардинг НЕ автоматичний
Класичний Azure SQL Database **сам таблиці не шардить**. Хочеш горизонтальний масштаб — робиш його **на рівні застосунку сам**, а Azure лише дає **інструменти-помічники** (Elastic Database tools).

## Як це роблять
- Дані розкидаєш по **кількох окремих БД** — кожна БД = **шард** (напр. по `tenant_id` чи діапазону ключів);
- **Shard Map Manager** — окрема БД-довідник, що тримає мапу «який ключ → у якій БД», і клієнтська бібліотека **маршрутизує** запит у потрібний шард;
- **Elastic Queries** — щоб зробити запит **поперек** шардів (повільніше);
- **Elastic Jobs** — прогнати one-and-the-same скрипт по всіх шардах (міграції тощо);
- **Elastic Pool** — не шардинг, а спосіб, щоб багато БД **ділили спільний бюджет ресурсів** (економія).

## Виграш
- Горизонтальний масштаб і **write-масштаб** (на відміну від Hyperscale — тут запис розкиданий по шардах);
- ізоляція тенантів (кожен у своїй БД);
- гнучкість — ти повністю контролюєш стратегію шардингу.

## Межа (головне)
- **Усе на тобі:** вибір ключа, розміщення, ребаланс, крос-шардові запити/транзакції — руками;
- **крос-шардові join'и/транзакції** дорогі й складні;
- більше операційної мороки, ніж у Cosmos/Citus, де шардинг вбудований.

**Суть (пара речень для співбесіди):** У класичному Azure SQL Database шардинг **DIY** — дані розкидаєш по **кількох БД-шардах** сам, а Azure дає **Elastic tools** (Shard Map Manager для маршрутизації, Elastic Queries/Jobs для роботи поперек). Дає **write-масштаб** та ізоляцію тенантів, але **вибір ключа й ребаланс — на тобі**, і крос-шардові операції дорогі. Треба «шардинг без мороки» — це Cosmos/Citus, а не SQL DB.
