# Azure Functions + Azure SignalR Service

Зв'язка для **serverless-реалтайму**: подієва обробка на боці бекенду + живий push статусу клієнту, без власних серверів.

## З чого складається

**Azure Functions** — event-driven serverless-компʼют. Одиниця = функція з одним **тригером** (Blob, Queue, Service Bus, Timer, HTTP, SignalR upstream…) і декларативними **біндингами** (вхід/вихід до ресурсів без SDK-бойлерплейту). Інстанси ефемерні й **stateless**, платформа сама масштабує. На плані **Consumption** — scale-to-zero й оплата **лише за виконання**.

**Azure SignalR Service** — керований реалтайм-backplane, що **тримає персистентні конекшни клієнтів замість твоїх серверів**. Прибирає з рівняння Redis-backplane і sticky sessions.

**Чому вони в парі:** ефемерна Function **фізично не може тримати персистентний конекшн**. Тому конекшн живе на SignalR Service, а функції лише **пушать у нього події** через SignalR output binding — адресно, по `userId`. У serverless-режимі це не «опція для економних», а **обов'язковий елемент**: без always-on сервера Redis-backplane сюди не приткнеш.

**Типовий потік:**
1. Браузер стукає в `/negotiate` (HTTP-Function із SignalR input binding) → дістає URL Сервісу + токен, конектиться до Сервісу.
2. Подія на бекенді (нове повідомлення в черзі, готовий етап обробки) тригерить Function.
3. Function через output binding пушить подію потрібному юзеру → клієнт оновлюється в реалтаймі.

## Наш випадок: живий статус довгої обробки

Задача класу **«залив великий файл → бекенд довго молотить етапами → покажи юзеру живий прогрес»** (конвертація відео, генерація важкого звіту, bulk-імпорт, рендер).

- Blob/Queue-тригери ганяють етапи конвеєра в Functions; залежні/паралельні кроки оркеструє **Durable Functions** (fan-out/fan-in).
- Кожне завершення етапу адресно пушиться юзеру через SignalR output binding → смужка прогресу рухається.

**Чому пачка тут рідна** (недоліки serverless не стріляють):
- навантаження **спайкове/подієве** → scale-to-zero й оплата лише за реальну обробку;
- **cold start неважливий** — 300 мс губляться на тлі десятків секунд обробки;
- **statelessness природна** — стан живе в Cosmos/черзі, не в пам'яті;
- конекшн і так мусить жити поза функцією → SignalR Service обов'язковий.

## Де це НЕ підходить

- **Рівний потік 24/7** (тікер котирувань, безперервна телеметрія на 100k клієнтів) → per-execution Functions під нон-стоп навантаженням **дорожчі** за пару always-on серверів. Вартість перевертається.
- **Потрібна миттєвість у мілісекундах** (чат, ігри, колаборативне редагування) → **cold start болить**. Або постійний сервіс, або хоча б Functions на **Premium/Flex** (прогріті інстанси), що вбиває сенс scale-to-zero.
- **Задача коротша за cold start** — накладні на підйом інстансу з'їдають виграш.

**Межа одним рядком:** пачка збс для **спайкового подієвого навантаження з довгими задачами**; погана — для **стабільно-високого потоку або латентно-чутливих мілісекундних** сценаріїв.
