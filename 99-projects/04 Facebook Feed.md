# Facebook News Feed — Azure-рішення

## Постановка проблеми
Юзери **постять**, **підписуються** одне на одного і бачать **стрічку** постів тих, на кого підписані. Масштаб: ~2 млрд юзерів, **read-heavy** (гортають постійно), **eventual** ок (стрічка на секунду застаріла — не біда).

Три болі, які й визначають вибір технологій:
- **Як зібрати стрічку (fan-out):** *push* — передрахувати стрічку при пості; *pull* — зібрати на читанні. **Гібрид:** звичайних юзерів push-иш, а **зірок** (мільйони підписників) не передраховуєш — їхні пости **домішуєш на читанні** (бо push у мільйони стрічок задорого).
- **Вірусний пост** — один **гарячий ключ**, який смикають мільйони.
- **Розкидання постів** по стрічках підписників — важке, робиться **async**.

Далі — як кожен біль закривається Azure-технологіями.

## 1. Cosmos DB — під стрічки/пости
- **Що:** керований NoSQL, шардований по partition key, еластичний, глобальний.
- **Чому сюди:** стрічку читають **по `userId`** («дай стрічку юзера X») — це point-read по partition key. Партиціонуєш по `userId` → **вся стрічка юзера на одній партиції** → швидке читання. Плюс read-heavy (гортають постійно), а **eventual** тут ок (стрічка на секунду застаріла — не біда) → береш слабший рівень консистентності = дешевше й швидше.
- **Ключове:** стрічки **незалежні** одна від одної → мультипартиційні транзакції не потрібні, і слабке транзакційне місце Cosmos **тут не болить** (на відміну від бронювання).

## 2. Azure Functions + черга — під async fan-out
- **Навіщо async:** коли юзер постить, **не можна** синхронно вписати пост у мільйони стрічок — POST-запит висітиме вічність. Тому: `пост → повідомлення в чергу → воркери у фоні розкидають`.
- **Черга = буфер + надійність:** сплеск постів черга **поглинає**, воркери вигрібають своїм темпом; воркер упав — повідомлення **лишилось у черзі й повториться**.
- **Azure Functions = воркери:** черго-тригерна Function **сама скейлиться під глибину черги** (багато повідомлень → більше інстансів → черга вигрібається; спорожніла → scale to zero, платиш за виконання).

**Storage Queue vs Service Bus (детальніше):**
- **Storage Queue** — гранично проста: повідомлення до 64 KB, enqueue/dequeue (з **visibility timeout** — поки обробляєш, повідомлення сховане; не видалив вчасно → з'явиться знову для ретраю), масштаб величезний, копійки. **Без порядку, без pub/sub.** Бери, коли треба просто **надійний дешевий буфер**.
- **Service Bus** — справжній брокер:
  - **Topics/Subscriptions (pub/sub):** одну подію «пост створено» ловлять **кілька незалежних споживачів** (оновлення стрічки + пуш-нотифікації + аналітика), кожен зі своєю підпискою. Storage Queue так **не вміє**;
  - **sessions** (FIFO), **dead-letter** (збійні самі відкладаються), **dedup**, транзакції.
- **Вибір:** fan-out — єдиний споживач і порядок не треба → **Storage Queue** (дешевше). Треба, щоб пост тригерив **багато речей** одразу → **Service Bus topics**.

## 3. Azure Cache for Redis (Premium, реплікація) — під гарячий ключ
- **Проблема:** вірусний пост = **один ключ**, який смикають мільйони.
- **Чому шардинг НЕ рятує:** шардинг розкидає **різні** ключі по нодах. А тут ключ **один** → живе на **одному** шарді → той шард усе одно горить. Шардинг ділить **простір ключів**, а не навантаження на **один** ключ.
- **Чому реплікація рятує:** тримаєш **багато копій** цього ключа на **репліках**; читання розмазуються по всіх репліках → жодна нода не плавиться. Тобто **шардинг = розкидати різні ключі; реплікація = розмазати читання ОДНОГО ключа**. Гарячий ключ потребує другого.

## 4. Курсорна пагінація — під читання стрічки
- Стрічку гортають сторінками. Передаєш **timestamp останнього побаченого** → отримуєш «старіші за це».
- **Чому не offset:** зверху **постійно падають нові пости**, тож offset би **дублював/пропускав** елементи під час гортання. Курсор по timestamp **стабільний**. У Cosmos це лягає на continuation-токен / `WHERE timestamp < cursor`.
