# URL Shortener — Azure-рішення

## Постановка проблеми
Юзер дає **довгий URL** → отримує **короткий код**; хтось клікає короткий → **редірект** на довгий. Сутності (довгий URL, короткий код) і API (`POST` створити, `GET` редіректнути) тривіальні — сигнал у deep dives.

Нефункціональне, що й визначає рішення:
- **read-heavy** — кліків набагато більше за створення (~100:1);
- **редірект має бути швидким** (він на критичному шляху кожного кліку);
- **код унікальний** (без колізій) і бажано **непередбачуваний** (не перебирається);
- **висока доступність** — старі лінки не мають ламатися.

Ключові виклики: (1) генерація коду, (2) де тримати атомарний лічильник, (3) швидкий редірект на масштабі, (4) тип редіректу.

## 1. Генерація коду → Sqids
- **Що:** Sqids (колишній **Hashids**) — бібліотека, що **оборотно** кодує ціле число в короткий URL-безпечний рядок і назад. Не хеш і не шифрування — **обфускація**.
- **Чому сюди:** треба код **унікальний і непередбачуваний**. Лічильник дає унікальність (немає колізій), але коди йдуть підряд → базу можна **спарсити перебором**. Sqids ховає послідовність, зберігаючи унікальність.
- **Ключове (контраст):** *лічильник* = унікальний, але передбачуваний; *хеш* = непередбачуваний, але колізії; **Sqids = найкраще від обох** (унікальність лічильника + непередбачуваність хешу). У .NET — `Sqids.NET`.

## 2. Атомарний лічильник → Azure SQL `SEQUENCE` (або Redis)
- **Що:** потрібен **атомарний монотонний лічильник**, що видає унікальні ID для Sqids.
- **Чому сюди / варіанти:**
  - **Azure SQL `SEQUENCE`** — самостійний об'єкт-лічильник на рівні схеми (не прив'язаний до колонки, на відміну від `IDENTITY`), `CACHE 1000` віддає діапазони з пам'яті. Durable за природою;
  - **Azure Cache for Redis** — `INCR`/`INCRBY` атомарні (однопоточний рушій виключає гонки); для масштабу видавай **діапазонами** (`INCRBY 1000`) і роздавай локально.
- **Ключове (контраст):** `SEQUENCE` при падінні може *пропустити* діапазон (діра), але **ніколи не видасть значення двічі** — а нам саме це й треба (дірки безпечні, повтори — ні). І 🚫 **не Cosmos:** один лічильник = один документ = **гаряча партиція** (усі записи в одну логічну партицію → throttling). Класичне «чому так не роблять».

## 3. Швидкий редірект на масштабі → Azure Front Door
- **Що:** глобальна L7-точка входу з edge-кешем і rules engine.
- **Чому сюди:** read-heavy (кліків у ~100 разів більше за створення), редірект хочеться віддавати **якнайближче до юзера**. Front Door **кешує гарячі коди й робить редірект на краю**, не доходячи до origin.
- **Ключове (контраст):** гарячі короткі коди осідають на **edge** → мільйони кліків **не б'ють у бекенд** (без кешу кожен клік ішов би аж до origin). Плюс маршрутизація між регіонами й розведення read/write. Найближчий Azure-аналог edge-редіректу (чесно — слабший за Cloudflare Workers).

## 4. Тип редіректу → 302, не 301
- **Що:** HTTP-редірект буває permanent (**301**) і temporary (**302**).
- **Чому 302:** **301** браузери/проксі кешують намертво → **втрачаєш аналітику кліків** і не можеш змінити/протермінувати ціль. **302** → кожен клік проходить через твій сервер.
- **Ключове (контраст):** *301* = швидше юзеру, але сліпо (нема аналітики, ціль не зміниш); *302* = кожен клік у тебе (аналітика + контроль). Для шортенера — **302**.
