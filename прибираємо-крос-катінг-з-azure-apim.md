# Azure API Management (API-шлюз)

**Проблема крос-катінгу.** У кожному сервісі є речі, які повторюються скрізь і не є бізнес-логікою: перевірка токена, rate limiting, кеш, логування. Якщо кожен сервіс реалізовує це сам — виходить дублювання, різнобій (у одному ліміт є, в іншому забули) і роздуті сервіси. Це і є **крос-катінг** — наскрізні турботи, які хочеться винести в одне місце.

Azure API Management — керований API-шлюз, що **виносить цей крос-катінг зі сервісів у політики на краю** — щоб .NET-бекенди лишалися тонкими.

**Що бере на себе (на краю, замість сервісів):**
- **автентифікація/авторизація** (JWT-валідація);
- **rate limiting і квоти**;
- **кеш** відповідей;
- трансформація й версіонування;
- **логування/метрики**.

**Політики** — конвеєр правил (XML), що застосовуються на стадіях запиту (inbound → backend → outbound). Уся магія шлюзу живе тут.

**API / Operations** — самі ендпоінти; **імпортуються з OpenAPI** твого minimal API/контролерів, тобто контракт не описуєш двічі.

**Кеш на краю** — знімає навантаження з бекенду під read-heavy патерни (згадай шортенер/дропбокс): популярні відповіді віддаються зі шлюзу, не доходячи до сервісу.

**Фасад для мікросервісів** — один фронт для багатьох бекендів.

**Де це оверкіл (щоб знати баланс):**
- **один дрібний сервіс** — вистачить вбудованого middleware, APIM тут зайвий;
- додає **хоп (латентність)** і **коштує** (виділені тіри недешеві);
- світиться лише коли **багато API / споживачів / крос-катінгу** — інакше це складність без вигоди.
