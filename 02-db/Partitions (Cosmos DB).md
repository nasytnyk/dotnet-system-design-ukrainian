# Партиціонування Cosmos DB

## Навіщо
Cosmos створений під **planet-scale** (глобально, еластично, реплікація по регіонах) — а одна машина має стелю (диск/CPU/RAM). Тому дані **мусять** розкидатися вшир, по багатьох машинах.

## Як
- Обираєш **partition key** (`userId`, `tenantId`…); Cosmos **хешує** його й кладе документи з однаковим ключем **разом** — у логічну партицію, а групи логічних живуть на **фізичних партиціях** (машинах).
- Cosmos **сам додає** фізичні партиції в міру росту й перебалансовує.

## Головний трейд-оф (звідси все)
- **Однопартиційний запит** (фільтр по partition key) → пряме влучання в **одну машину** → швидко й дешево. Щасливий шлях, під який Cosmos заточений.
- **Крос-партиційний** (без ключа / діапазон по багатьох) → **fan-out** по багатьох машинах + злиття → дорого по **RU**, а пагінація — тільки через continuation-токени.

## Головне правило
Обирай partition key так, щоб **найгарячіші запити лишалися однопартиційними**. Збіг ключа з патерном доступу = дешево й швидко; постійний fan-out = **воюєш із дизайном**.

## Пастка: гаряча партиція
Поганий ключ → весь трафік летить в **один** ключ = вся нагрузка на **одну машину** → уколошкана сама ідея розподілу. Класика: **один лічильник = один документ = hot partition**.

**Суть:** Cosmos шардить дані по машинах через **хеш partition key** заради горизонтального масштабу; ключ вибираєш під свої запити, щоб гарячі лишались **однопартиційними** (дешево), а не перетворювались на **fan-out** (дорого). Поганий ключ = **гаряча партиція**.
